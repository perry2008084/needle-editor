# Project Needle MVP PRD（v0.1）

## 1. 产品名称
先用代号：**Project Needle**  
意思很简单：轻、快、准。

---

## 2. 产品定位

一款 **轻量、高性能、界面简洁优雅** 的代码编辑器，  
面向偏键盘驱动、追求响应速度的开发者，  
并提供 **Sublime Text 插件生态的部分兼容能力**，降低迁移成本。

---

## 3. 产品目标

### 核心目标
1. **启动快**
2. **编辑流畅**
3. **内存占用低**
4. **基础工作流完整**
5. **兼容一批高价值 Sublime 插件**

### 非目标（MVP 不做）
1. 不追求完整 IDE 能力
2. 不追求 100% Sublime API 兼容
3. 不做完整调试器
4. 不做内置终端大而全
5. 不做复杂协作功能

---

## 4. 目标用户

### 第一批用户
- 现有 Sublime Text 用户
- 不喜欢 VS Code 内存占用的开发者
- 偏好键盘工作流的工程师
- 前后端/脚本/配置文件重度编辑用户

### 典型画像
- 希望编辑器“秒开”
- 经常同时开很多文件
- 喜欢 Command Palette、多光标、快速查找
- 有自己的插件习惯，但不一定需要全兼容

---

## 5. 用户核心价值

用户希望：

- 打开编辑器时：**快**
- 打开大文件时：**稳**
- 输入和多光标时：**顺**
- 搜索、跳转、命令执行时：**丝滑**
- 从 Sublime 迁移时：**不用从零重建习惯**

---

## 6. MVP 功能范围

### 6.1 编辑器核心能力
#### 必做
- 打开/保存文件
- 多标签页
- 多光标 / 多选区
- undo / redo
- 查找 / 替换
- 行号、缩进、软换行
- 基础代码折叠
- 文件拖入打开
- 最近文件列表

#### 验收标准
- 100MB 纯文本文件可打开
- 多光标常见操作无明显卡顿
- 大文件滚动和搜索不应出现明显冻结

---

### 6.2 命令系统
#### 必做
- Command Palette
- 命令注册与执行
- 快捷键绑定
- 菜单/命令面板项配置

#### 验收标准
- 命令响应时间短
- 插件注册命令后可立即出现
- 可通过快捷键触发内建命令与插件命令

---

### 6.3 配置系统
#### 必做
- 用户设置
- 项目设置
- 快捷键配置
- 主题/配色设置
- 类似 Sublime 的 JSON 配置体验

#### 验收标准
- 修改配置可热加载
- 用户配置优先级清晰
- 可导入基础 Sublime 配置习惯

---

### 6.4 语法高亮
#### MVP 范围
- 内置常见语言高亮：
  - JS/TS
  - Python
  - Go
  - Rust
  - JSON
  - Markdown
  - YAML
  - HTML/CSS
  - Shell

#### 不强求
- 不在 MVP 做极复杂 syntax engine 兼容
- 不先追求和 Sublime 完全一样的语法系统

---

### 6.5 项目能力
#### 必做
- 打开文件夹 / 项目
- Sidebar 文件树
- 全局模糊搜索文件
- 项目内文本搜索（基础版）
- 最近项目

#### 验收标准
- 中型项目文件检索速度可接受
- 文件切换、模糊搜索体验足够快

---

### 6.6 Sublime 插件兼容（MVP 子集）
#### 目标
兼容“高价值纯 Python 插件子集”。

#### MVP 支持内容
- 包目录结构兼容
- 加载本地 package
- `sublime` 基础模块
- `sublime_plugin` 基础模块
- `TextCommand`
- `WindowCommand`
- `ApplicationCommand`
- `EventListener` 的一部分常用事件
- settings 访问
- `run_command`
- `set_timeout` / 基础异步调度
- `View` / `Window` / `Region` / `Selection` 基础对象

#### 明确不保证
- 所有插件可直接运行
- 所有 UI 类 API 完整支持
- 所有历史 undocumented behavior 兼容

---

### 6.7 包管理能力
#### MVP
- 安装本地 `.sublime-package`
- 从指定仓库安装 package
- 启用/禁用/卸载 package
- 插件热加载/重载
- 依赖包基础处理

#### 暂不要求
- 完整复刻 Package Control 全部行为
- 完全同步其所有仓库生态规则

---

## 7. 用户体验目标

### 产品感觉
- 默认界面极简
- 弱干扰、低噪音
- 高密度但不压迫
- 键盘优先
- 状态反馈克制而清晰

### 性能目标（MVP）
- 冷启动：**< 500ms ~ 1.5s**（看平台和语言实现）
- 空白启动内存：**显著低于 VS Code**
- 多标签切换：接近即时
- Command Palette：基本秒开
- 搜索与文件跳转：低延迟

---

## 8. 技术架构要求

### 架构原则
- 编辑器核心与插件运行时隔离
- 插件崩溃不拖死主 UI
- 文本编辑、渲染、索引、插件调用解耦
- API 兼容通过“适配层”实现，不污染内核设计

### 模块划分
1. **Core**
   - Buffer
   - Selection
   - Undo/Redo
   - Command bus
   - Config
   - Project model

2. **UI**
   - Window
   - Tabs
   - Sidebar
   - Palette
   - Panels
   - Theme rendering

3. **Syntax/Index**
   - Tokenization
   - Search
   - Symbol index（后续）

4. **Plugin Host**
   - CPython runtime
   - sublime / sublime_plugin shim
   - package loader
   - event dispatcher

5. **IPC Layer**
   - 主进程 ↔ plugin_host 通信
   - 命令调用
   - 事件分发
   - 对象句柄映射

---

## 9. 兼容性策略

### 原则
- 优先兼容常用插件工作流
- 优先兼容 API 主路径
- 对边角行为采用“文档化差异”策略

### 交付形式
发布一个 **Compatibility Matrix**
- Fully Supported
- Partially Supported
- Not Yet Supported

---

## 10. 成功指标（MVP）

### 产品指标
- 用户可完成日常文件编辑工作流
- 至少兼容 10~20 个目标插件中的多数
- 启动速度与内存成为明确优势

### 技术指标
- 插件崩溃不拖垮编辑器
- 文本核心在大文件下稳定
- API 兼容测试可自动回归

# 二、推荐 MVP 技术方案

## 推荐栈
### 方案 A（推荐）
- **Rust**
- 自研文本核心（rope/piece tree）
- UI：先用成熟 GUI 壳，后续再逐步自绘
- 插件宿主：独立 Python 进程
- IPC：JSON-RPC 起步

### 原因
- 先把“快、稳、轻、兼容”四件事做出来
- 别第一天就冲进自绘宇宙和字体渲染黑洞

# 三、里程碑计划

## Milestone 0：预研与立项（2~4 周）

### 目标
明确边界，别一开始就幻想“重写世界”。

### 输出物
- 技术选型结论
- 架构草图
- 兼容性目标清单
- 样本插件列表（10~20 个）

### 必做事项

- 定义 Buffer/Selection/Command 抽象
- 列出第一版支持的 Sublime API
- 定义 package 目录和加载规则
- 选 10~20 个目标插件做 smoke test 样本

### 里程碑通过标准
- 能讲清楚：做什么、不做什么、怎么验收

---

## Milestone 1：编辑器骨架（第 1~2 个月）

### 目标
做出能编辑文件的“壳”。

### 功能
- 单窗口、多标签
- 打开/保存文件
- 文本显示与输入
- 光标移动、选择、复制粘贴
- undo/redo
- 查找/替换
- 基础设置系统
- 快捷键系统
- 命令系统基础

### 验收
- 可稳定作为普通文本编辑器使用
- 小文件编辑流畅
- Command Palette 初版可用

---

## Milestone 2：高性能文本体验（第 3~4 个月）

### 目标
让它开始“像个像样的编辑器”。

### 功能
- 多光标
- 大文件支持
- 增量渲染
- 模糊文件搜索
- 项目/文件夹打开
- Sidebar
- 基础语法高亮
- 最近文件/项目

### 验收
- 100MB 文本可打开
- 多光标不卡
- 文件切换和搜索响应快
- 内存占用明显优于 Electron 系产品

---

## Milestone 3：插件宿主 MVP（第 5~6 个月）

### 目标

### 功能
- 独立 `plugin_host`
- 嵌入 Python
- package 扫描与加载
- `sublime` / `sublime_plugin` 基础模块
- `TextCommand / WindowCommand / ApplicationCommand`
- `run_command`
- 基础 `View / Window / Region / Selection`
- EventListener 常用事件

### 验收
- 至少 3~5 个简单插件可运行
- 插件崩溃后编辑器不崩
- 插件热重载可用

---

## Milestone 4：插件生态接入（第 7~8 个月）

### 目标
让用户第一次感受到“能迁移”。

### 功能
- 本地 `.sublime-package` 安装
- 简单仓库源安装
- 启用/禁用/卸载 package
- settings / keymap / commands 兼容
- 菜单和命令面板扩展支持

### 验收
- 目标插件列表中 10 个左右能部分或完整运行
- 包管理流程可自举
- 用户能迁移一部分配置习惯

---

## Milestone 5：高级 API 与体验打磨（第 9~10 个月）

### 目标
把“能跑”推进到“敢试日常使用”。

### 功能

### 验收
- 典型编码工作流可连续使用数小时
- 常见插件不频繁报错
- UI 基本达到“简洁优雅”的第一版

---

## Milestone 6：Public Beta（第 11~12 个月）

### 目标

### 功能

# 四、单人版压缩路线（更现实）

如果你一个人先搞原型，我建议压成 3 个阶段：

## 阶段 A：8~10 周
- 基础编辑器
- 命令系统
- 配置系统
- 多光标
- 查找替换
- 文件树/模糊搜索

## 阶段 B：6~8 周
- plugin_host
- Python shim
- 跑通简单 TextCommand 插件
- 包扫描、热重载

## 阶段 C：6~8 周
- 安装本地 package
- 兼容 5~10 个目标插件
- 打磨启动速度和内存

这样你 **4~6 个月能拿出一个很像样的 PoC**。

# 六、技术风险清单

## 高风险
- Sublime API 行为兼容不足
- 事件时序不一致导致插件诡异失效
- 文本核心返工
- 跨平台输入法/字体/窗口细节
- 高亮和搜索在大项目下性能不稳

## 中风险
- Python 运行时版本兼容
- Package 生态接入复杂度高于预期
- UI 框架限制未来性能优化

## 低风险
- 基础设置系统
- 命令面板
- 本地包加载
- 主题系统基础版

---

# 七、建议你立刻做的 5 件事

## 1. 定义“目标插件清单”
别空谈生态，先列样本。建议 15 个以内，按类别挑。

## 2. 定义“兼容 API 最小集合”
把 MVP 要支持的 `sublime` / `sublime_plugin` 接口列出来。

## 3. 先做文本核心 PoC
拿真实大文件测：
- 打开
- 搜索
- 多光标
- 滚动
- undo/redo

## 4. 先做 plugin_host 通路
哪怕只支持一个 `TextCommand`，也要尽早打通。

## 5. 建自动化回归
每增加一个 API，都拿目标插件跑一遍 smoke test。

---

# 八、最终建议

战略上遵循这句话：

> **先做“轻量编辑器”，再做“高价值兼容层”，不要反过来。**

原因：
- 真正吸引人的，是快和顺
- 真正留住人的，是兼容迁移成本低
- 真正拖死项目的，是一开始就想 100% 复刻
