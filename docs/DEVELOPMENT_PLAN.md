# Project Needle 详细开发方案（v0.1）

## 1. 文档目标

本文档用于把 PRD 和架构设计转成可执行的研发计划，适合作为：

- 创始人/主程的开工路线图
- 小团队分工依据
- 里程碑管理文档
- 原型到 Beta 的落地计划

重点不是“未来也许”，而是“下一步具体干什么”。

---

## 2. 开发总策略

## 2.1 开发原则

1. **先做编辑器核心，再做插件兼容**
2. **先打通端到端链路，再补深度能力**
3. **先做高价值 API，再碰边角兼容**
4. **每一阶段都要有可验证产物**
5. **性能和稳定性不是收尾项，是全程项**

## 2.2 研发主线

整个开发分为 6 条主线并行推进：

1. 文本核心
2. UI 与交互
3. 命令与配置系统
4. 插件宿主与 API 兼容
5. 包管理与生态接入
6. 测试、性能、打包

---

## 3. 阶段划分总览

| 阶段 | 周期 | 核心目标 | 关键产物 |
|---|---:|---|---|
| Phase 0 | 2~4 周 | 预研与技术打样 | 技术结论、样本插件清单、PoC |
| Phase 1 | 4~6 周 | 基础编辑器可用 | 文件编辑、命令系统、配置系统 |
| Phase 2 | 4~6 周 | 高性能编辑体验 | 多光标、大文件、搜索、项目视图 |
| Phase 3 | 4~6 周 | 插件宿主打通 | plugin_host、基础 shim、简单插件运行 |
| Phase 4 | 4~6 周 | 包管理与兼容增强 | package 安装、重载、更多 API |
| Phase 5 | 6~8 周 | Beta 打磨 | 稳定性、性能、跨平台、文档 |

如果是单人开发，整个周期建议按 5~6 个月 PoC、9~12 个月 Beta 来看。

---

## 4. Phase 0：预研与技术打样

## 4.1 目标
在正式编码前确认高风险问题，不让项目在第 3 个月突然发现基础假设错了。

## 4.2 工作内容

### A. 技术选型
- 确定 Rust 版本与基础工程结构
- 确定 UI 路线（成熟 GUI 壳优先）
- 确定文本存储数据结构（Rope / Piece Tree）
- 确定 IPC 方案（JSON-RPC）
- 确定 Python 嵌入方式和 plugin_host 进程模型

### B. 风险打样
做 3 个 PoC：

#### PoC-1：文本核心
验证：
- 插入删除性能
- 多光标批量编辑
- line/column 映射
- 100MB 文本打开与滚动能力

#### PoC-2：渲染
验证：
- 可见区虚拟化
- 文本布局与滚动性能
- 光标、选区、行号渲染

#### PoC-3：插件宿主
验证：
- 独立 Python 进程启动
- shim 模块注入
- 主进程 RPC 调用
- 跑通一个最小 `TextCommand`

### C. 兼容清单准备
- 选择 10~20 个目标插件
- 按类型分类：命令类、文本处理类、UI 类、补全类
- 为每个插件定义“可运行”的最低标准

## 4.3 输出物
- 技术选型决议
- 风险清单
- 样本插件列表
- PoC 结论记录

## 4.4 通过标准
- 至少证明：文本核心方案可行、plugin_host 通路可行、UI 路线可落地

## 5. Phase 1：基础编辑器可用

## 5.1 目标
做出一版可作为普通文本编辑器使用的产品骨架。

## 5.2 功能范围

### 核心编辑
- 新建/打开/保存文件
- 多标签页
- 光标移动
- 基础选区
- 复制/粘贴/剪切
- undo/redo

### UI 基础
- 主窗口
- 标签栏
- 状态栏（可选简版）
- 文件关闭提示

### 命令系统
- 命令注册表
- 命令执行器
- Command Palette 初版

### 配置系统
- 用户设置文件
- 快捷键配置文件
- 热加载

## 5.3 工程拆解

### Core 任务
- 实现 Buffer 基础接口
- 实现 View 与 Buffer 绑定
- 实现单光标/单选区
- 实现 undo/redo 事务雏形

### UI 任务
- 基础文本区渲染
- 标签栏切换
- 文件打开保存对话流程
- 状态提示信息

### 系统任务
- 命令注册中心
- 设置文件加载器
- 日志基础设施

## 5.4 交付标准
- 可以日常编辑小文件
- 程序稳定运行 30 分钟以上不出现明显状态错乱
- 基础快捷键可用
- 配置变更可热生效

---

## 6. Phase 2：高性能编辑体验

## 6.1 目标
从“能用”升级到“有点上头”。

## 6.2 功能范围

### 编辑增强
- 多光标 / 多选区
- 行操作（复制行、删除行、移动行）
- 查找 / 替换
- 跳转到行
- 代码折叠基础版

### 项目能力
- 打开文件夹
- Sidebar 文件树
- 最近项目
- 模糊文件搜索
- 项目内文本搜索基础版

### 性能增强
- 大文件支持
- 增量布局
- 可见区渲染
- 行缓存与字体度量缓存

### 语法高亮
- 支持主流语言基础高亮
- 支持按文件类型切换语法

## 6.3 工程拆解

### 文本核心任务
- 多选区数据模型
- 编辑后区间映射
- 行索引缓存
- 快照机制

### 渲染任务
- viewport virtualization
- 局部重绘
- token 缓存接口

### 项目能力任务
- 文件树构建
- 模糊搜索索引
- 搜索任务后台化

## 6.4 交付标准
- 100MB 文件可打开
- 多光标操作不明显卡顿
- 滚动和文件切换流畅
- 搜索不会阻塞 UI 主线程

---

## 7. Phase 3：插件宿主与基础兼容

## 7.1 目标
让第一个 Sublime 风格插件真正跑起来。

## 7.2 范围定义
本阶段只做高价值兼容子集，不碰全量复刻。

### 必做 API
#### `sublime`
- active_window
- set_timeout
- load_settings
- status_message（基础版）
- error_message（基础版）

#### `sublime_plugin`
- TextCommand
- WindowCommand
- ApplicationCommand
- EventListener

#### 对象模型
- Window
- View
- Settings
- Region
- Selection

#### 行为接口
- run_command
- 插件命令注册/发现
- 常用事件派发

## 7.3 工程拆解

### plugin_host 任务
- Python 进程启动器
- shim 注入
- package 扫描器
- 插件加载器
- 异常捕获器

### 主进程任务
- Plugin Bridge
- View/Window 句柄管理
- RPC 请求分发器
- 命令与事件同步器

### 兼容测试任务
- 最小测试插件集
- 命令注册回归测试
- 事件顺序测试

## 7.4 交付标准
- 能加载本地 package
- 能执行至少 3 个简单纯 Python 插件
- 插件异常不导致主进程退出
- 支持插件热重载基础流程

---

## 8. Phase 4：包管理与兼容增强

## 8.1 目标
让生态开始“有迁移价值”。

## 8.2 功能范围

### 包管理
- 安装本地 `.sublime-package`
- 安装目录形式 package
- 启用/禁用 package
- 卸载 package
- package reload

### 配置兼容
- User package 特殊优先级
- settings 合并规则增强
- key bindings / commands / menu 扩展支持

### API 增强
- 更多 EventListener 事件
- input panel
- quick panel 基础版
- 简单 completion 支持

## 8.3 工程拆解

### Package Manager 任务
- 包状态机
- 安装卸载事务
- 包索引刷新机制
- metadata 解析

### API 增强任务
- UI 面板与插件系统对接
- completion 回调机制
- 命令可见性/可用性查询完善

### 兼容性任务
- 扩展样本插件到 10~20 个
- 兼容矩阵初始化
- 记录差异行为

## 8.4 交付标准
- 目标插件中有一批能直接用
- 包管理不易把状态搞炸
- 用户可以迁移一部分 Sublime 工作流

## 9. Phase 5：Beta 打磨与发布准备

## 9.1 目标
让它不只是能演示，而是能给外部用户骂——被用户骂是 Beta 的基本礼仪。

## 9.2 核心工作

### 稳定性
- 崩溃排查
- 内存泄漏定位
- 插件 reload 稳定性
- 配置热加载异常处理

### 性能
- 启动时间 profiling
- 打开大文件 profiling
- 搜索与命令执行 profiling
- 插件调用热点分析

### 产品化
- 设置界面基础版（可选）
- 首屏欢迎/迁移说明（简版）
- 日志导出
- 崩溃报告收集方案

### 发布
- Windows/macOS/Linux 打包
- 文档站点
- 已知问题列表
- 兼容性矩阵发布

## 9.3 交付标准
- 有外部可安装版本
- 有清晰文档
- 有已知问题说明
- 有能反馈问题的渠道

## 12. 人力配置建议

## 12.1 单人模式
优先级顺序：
1. Buffer/View/Command
2. 多光标与搜索
3. plugin_host 通路
4. 包管理
5. UI 打磨

### 单人节奏建议
- 每两周一个可跑版本
- 每阶段只解决一个主要风险
- 不同时开太多战线

## 12.2 3 人小团队模式

### 角色 A：Core/性能
- 文本存储
- 渲染性能
- 搜索/索引

### 角色 B：平台/UI
- 窗口/视图/面板
- 交互系统
- 主题与平台适配

### 角色 C：插件/生态
- plugin_host
- shim/API 兼容
- package manager
- 兼容性测试

## 14. 风险管理方案

## 14.1 最大风险

### 风险 1：文本核心返工
应对：
- 尽早做大文件与多光标 PoC
- 在 Phase 0 就验证

### 风险 2：插件兼容泥潭
应对：
- 先兼容高价值子集
- 建兼容矩阵，不瞎承诺

### 风险 3：UI 路线卡死
应对：
- 首版先成熟 GUI 壳
- 自绘放到后续优化阶段

### 风险 4：跨平台细节爆炸
应对：
- 平台能力抽象单独模块化
- 先优先支持一个主平台，再扩展

## 17. 最终建议

一句话版本：

> **用工程纪律做这个项目，不要用理想主义硬扛。**

更具体一点：
- 核心先稳
- API 先窄后宽
- 兼容先主路后边角
- 性能从第一天盯
- 每阶段都产出可运行版本

这样做，才有机会做出一个不只是“像 Sublime”，而是真的值得人迁移过去的编辑器。
