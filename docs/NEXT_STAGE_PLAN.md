# Project Needle 下一阶段开发清单（2026-05）

## 1. 目标

这份清单用于承接当前 `v0.2.x` 之后的开发，目标不是“功能越多越好”，而是：

> **把当前已经有雏形的桌面编辑器，推进到“可较顺手日常试用”的阶段。**

建议优先补的不是插件生态，而是当前编辑器本体最影响手感的短板：
- 编辑同步与 selection/cursor 语义
- 配置系统完整度
- 搜索与项目能力服务化
- 语法高亮基础版

---

## 2. 优先级总览

| 优先级 | 主线 | 目标 |
|---|---|---|
| P0 | 编辑体验收口 | 让当前版本不只是“能用”，而是更顺手 |
| P0 | 配置系统补全 | 建立用户级 settings / keymap / 合并规则 |
| P0 | 搜索能力服务化 | 让 Quick Open / Find in Project 不再主要依赖 UI 层同步扫描 |
| P1 | 项目模型增强 | 让项目能力更稳、更像真正的项目编辑器 |
| P1 | 语法高亮基础版 | 补上最显眼的编辑器缺口 |
| P2 | plugin_host 预研恢复 | 在本体更稳后再回到兼容层主线 |

---

## 3. P0：编辑体验收口

## 3.1 文本同步与 selection / cursor 语义

### 目标
减少“功能有了但手感别扭”的问题，让编辑行为更稳定、更可预期。

### 建议任务
- 细化 GUI → core 的文本同步粒度
- 细化 core → GUI 的同步与刷新时机
- 收口光标位置与选区更新规则
- 为常见编辑动作补 selection 回归测试
- 明确单选区与未来多选区的行为边界

### 建议拆成 Issue
- `UI-EDIT-001` 更细粒度文本同步
- `UI-EDIT-002` cursor / selection 更新规则整理
- `TEST-EDIT-001` 常见编辑动作回归测试

### 验收标准
- 连续输入、撤销、切标签、保存后不出现明显状态错乱
- 查找跳转、Goto Line、行操作后光标位置可预期
- 不因为一次 UI 刷新把 selection 弄飞

---

### 目标

### 建议任务

- 实现用户全局 keymap
- 明确默认 / 用户 / 项目配置合并顺序
- 增加配置校验与错误提示
- 打通配置变更广播

### 对应 `TASK_BREAKDOWN.md`

- `CFG-003`
- `CFG-004`
- `CFG-005`

### 建议拆成 Issue

- `CFG-USER-002` 用户全局 keymap 文件
- `CFG-MERGE-001` 配置层级合并规则
- `CFG-VALIDATE-001` 配置校验与错误提示

## 5. P0：搜索能力服务化

## 5.1 Quick Open / Find in Project 从 UI 逻辑过渡到模块化服务

### 目标
把当前“基础能用”的搜索能力，推进到“结构正确、后续可扩展”。

### 建议任务
- 将 Quick Open 索引与匹配逻辑逐步沉入 `crates/search`
- 将项目搜索逻辑抽成后台任务接口
- 为搜索结果增加取消、增量返回或批次返回能力
- 改善模糊排序
- 避免搜索阻塞 UI 主线程

### 对应 `TASK_BREAKDOWN.md`
- `SEARCH-001`
- `SEARCH-003`
- `PERF-004`

### 建议拆成 Issue
- `SEARCH-SVC-001` `crates/search` 文件索引基础版
- `SEARCH-SVC-002` Quick Open 改接搜索模块
- `SEARCH-SVC-003` Find in Project 后台任务化
- `SEARCH-SVC-004` 搜索结果批量返回 / 取消

### 验收标准
- 中型项目搜索不明显卡 UI
- Quick Open 与项目搜索都不再依赖 UI 线程现算全量结果
- 搜索代码不再主要散落在 `crates/ui`

## 6. P1：项目模型增强

## 6.1 从“能开项目”升级到“像个项目编辑器”

### 目标
让当前的 Open Folder / Sidebar / Recent Projects / watcher 基础版真正形成完整工作流。

### 建议任务
- 整理项目根目录状态模型
- 增加项目状态持久化
- 为 Sidebar 增加更稳的数据刷新机制
- 增加文件状态装饰（至少 dirty / open / active 的基础态）
- 梳理 watcher 与轮询回退之间的关系

### 对应 `TASK_BREAKDOWN.md`
- `CORE-007`
- `UI-008`
- `UI-006`

### 建议拆成 Issue
- `PROJECT-001` 项目状态模型整理
- `PROJECT-002` 项目状态持久化
- `PROJECT-003` Sidebar 数据刷新与装饰
- `PROJECT-004` watcher / polling 协同策略整理

### 验收标准
- 重新打开项目时，能恢复合理的项目上下文
- Sidebar 状态刷新更稳，少出现“树和实际状态不一致”

## 7. P1：语法高亮基础版

## 7.1 补齐“编辑器观感最明显的缺口”

### 目标
先做一个可接受的 v0 版本，不追求一步到位。

### 建议任务
- 建立 extension → syntax mapping
- 定义 tokenizer / syntax service 接口
- 先支持少量高频语言：Rust / JSON / Markdown / Python / TS
- 做基础高亮渲染
- 先接受“全文件重算的简版”，后续再做增量 token 更新

### 对应 `TASK_BREAKDOWN.md`
- `SYNTAX-001`
- `SYNTAX-002`
- `SYNTAX-003`

### 建议拆成 Issue
- `SYNTAX-001` 文件类型识别
- `SYNTAX-002` syntax service 接口
- `SYNTAX-003` 首批语言支持
- `UI-SYNTAX-001` UI 高亮接线

### 验收标准
- 打开主流文本代码文件后，能看到基础高亮
- 不要求一开始就支持全部语言
- 不要求第一版就做完增量刷新

## 9. 推荐开发顺序（现实版）

如果只按未来 2~4 周的现实节奏，我建议这样排：

1. **编辑同步 / selection 语义**
2. **用户级 settings / keymap / 合并规则**
3. **搜索服务化（先 Quick Open，再 Find in Project）**
4. **项目模型与 Sidebar 增强**
5. **语法高亮基础版**
6. **plugin_host Phase 3 预研恢复**

这个顺序的好处是：
- 先补“最影响手感”的部分
- 再补“最影响产品感”的部分
- 最后再回到“最影响长期价值”的插件主线

不然很容易出现一种经典惨剧：

> 插件兼容梦想很丰满，结果本体编辑手感还像个半熟煎蛋。

---

## 10. 一句话结论

下一阶段最该做的，不是再堆一批零散功能，而是把这四条主线补齐：

- **编辑体验收口**
- **配置系统完整化**
- **搜索 / 项目能力服务化**
- **语法高亮基础版**

这四条线补完，Needle 才会从“已经长起来的楼”变成“真的开始能住人的楼”。
