# Project Needle 下一阶段开发清单（2026-05）

## 1. 当前阶段判断

经过最近这一轮推进，原先定义的 P0 主线已经**基本收口**：

- 编辑同步与 selection / cursor 语义基础版 ✅
- 用户级 settings / keymap / 合并规则 / 基础校验 ✅
- 搜索服务化基础版（Quick Open / Find in Project）✅
- Find in Project 后台任务 + 取消机制 ✅
- 当前文件查找高亮基础版 ✅

因此，下一阶段不再建议继续围着 P0 小修小补打转，而是正式切到 **P1**。

> **接下来要解决的核心问题，已经从“能不能用”切换为“像不像个真正编辑器”。**

---

## 2. 下一阶段主目标

未来 2~4 周，建议集中在这三条主线：

1. **语法高亮基础版**
2. **项目模型与 Sidebar 增强**
3. **性能与大文件验证第一轮**

插件宿主和兼容层仍重要，但建议放在这三条线之后恢复，不要重新把战线拉爆。

---

## 3. P1-1：语法高亮基础版

### 目标
补齐当前编辑器最显眼的观感缺口。

### 建议任务
- 建立 extension → syntax mapping
- 定义 tokenizer / syntax service 接口
- 接入首批语言：Rust / JSON / Markdown / Python / TS
- 将高亮结果接到 UI
- 第一版可接受较粗实现，后续再做增量 token 更新

### 验收标准
- 打开常见代码文件能看到基础高亮
- UI 层已经能消费 `crates/syntax` 的结果
- 第一版不要求覆盖全部语言，也不要求增量高亮

---

## 4. P1-2：项目模型与 Sidebar 增强

### 目标
让当前“能打开项目”升级成“像个项目编辑器”。

### 建议任务
- 整理项目状态模型
- 提炼 Sidebar 所需共享状态
- 增加 active / open / dirty 基础状态装饰
- 梳理 watcher / polling 协同策略
- 增加最小项目状态持久化

### 验收标准
- Sidebar 状态刷新更稳
- 当前文件与已打开文件更容易识别
- 重开项目时能恢复合理上下文

---

## 5. P1-3：性能与大文件验证第一轮

### 目标
别再靠“感觉应该还行”，开始建立最小性能证据。

### 建议任务
- 做 10MB / 50MB / 100MB 文件打开 smoke test
- 记录打开时间与基本交互表现
- 检查搜索和滚动是否出现明显卡顿
- 初步定位最容易炸的路径

### 验收标准
- 至少形成一轮可复用的性能记录
- 能明确下一步性能工作重点，而不是继续猜

---

## 6. P1-4：插件主线恢复前准备

### 目标
不立刻全面开打 plugin_host，但先把 Phase 3 的最小闭环定清楚。

### 建议任务
- 选 3 个最小样本插件
- 明确第一批必做 API
- 明确 smoke test 目标

### 验收标准
- plugin_host 主线恢复时，不再从一团雾里起步

---

## 7. 推荐顺序

我建议的现实顺序是：

1. **语法高亮基础版**
2. **项目模型 / Sidebar 增强**
3. **性能与大文件验证**
4. **plugin_host 预研恢复**

原因很简单：
- 语法高亮最影响第一眼观感
- 项目模型最影响“像不像产品”
- 性能验证最影响后续会不会返工
- plugin_host 是长期价值线，但别在本体刚稳住时又把自己拖进兼容泥潭

---

## 8. 一句话结论

P0 现在已经不是主战场了。接下来该补的，是：

- **语法高亮**
- **项目模型**
- **性能证据**

把这三条线补起来，Needle 才会从“开始能住人”变成“住进去不会总想骂街”。
